# REVIEW.md — чек-лист независимого ревью PR

Этот файл — опорный чек-лист независимого ревью каждого PR репозитория
`skaffman41/ai-for-developers-project-387`, включая автоматическое ревью read-only
сессией CLI и ручное ревью. Каждый пункт проверяется по diff PR, файлам репозитория
и описанию PR, составленному по [шаблону](.github/pull_request_template.md), без
доступа к живому GitHub.

Правила применения:

- Сначала определи тип PR по описанию: инфраструктурный (workflow, документация,
  agent-контур) или изменяющий календарь (backend, frontend, контракт, тесты).
  Тип определяет, какие разделы критичны.
- Проверка календаря фиксирует согласованность изменений со спецификацией,
  сохранность данных и безопасные миграции. Изменение схемы SQLite версии 3 или
  функциональности календаря не запрещено навсегда: оно допустимо, когда PR
  согласован, данные сохраняются и миграция безопасна. Дефект — не сам факт
  изменения, а изменение без соблюдения этих условий.
- Для каждого пункта указано «Проверять» и «Дефект». Пункт без понятного
  «Дефекта» не считается проверенным.
- Каждое замечание ревью должно содержать файл, строку, условия возникновения и
  последствия; при отсутствии дефектов ревью сообщает это явно.

## 1. Календарная функциональность и пользовательские гарантии

Область: `backend/src/`, `frontend/src/`, `tests/`, поведение приложения.

- Проверять: для инфраструктурного PR — diff не затрагивает календарную
  функциональность (`backend/src/`, `frontend/src/`, `contract/main.tsp`,
  календарные тесты); для PR календаря — каждое изменение поведения связано с
  согласованной спецификацией или тикетом, указанным в описании PR.
  Дефект: изменение календаря без ссылки на согласованный spec/тикет либо
  незаявленное затрагивание календаря в инфраструктурном PR.
- Проверять: правила доступности не ослаблены неявно — будни (пн–пт), окно
  09:00–18:00 в зоне Europe/Moscow (UTC+03:00), сетка 30 минут, полный интервал
  встречи в пределах рабочего дня, прошедшие начала исключаются, окно
  бронирования — 14 дней от текущей московской даты. Изменение любого из этих
  правил допустимо только как согласованный PR календаря с обновлёнными тестами.
  Дефект: изменение правил без обновления тестов доступности и без указания в
  описании PR.
- Проверять: зона Europe/Moscow сохраняется в расчёте и отображении времени
  (дата окна доступности, границы слота, показ времени гостю и владельцу).
  Дефект: замена на UTC или локальную зону раннера, не оговорённая в
  спецификации PR.
- Проверять: попытки и повторы остаются идемпотентными — результат попытки
  сохраняется по паре `(operation, attempt_key)` с исходным payload; повторная
  отправка тех же данных возвращает сохранённый результат; тот же ключ с другими
  данными даёт конфликт `IDEMPOTENCY_KEY_REUSED`; после неопределённого COMMIT
  транзакция не выполняется повторно, восстановление — через новый HTTP-запрос
  с тем же ключом.
  Дефект: потеря сохранённого результата попытки, повторное выполнение
  побочных эффектов, молчаливая перезапись результата под тем же ключом.
- Проверять: запись не допускает двойных бронирований — проверка пересечения
  интервалов и вставка происходят в одной транзакции (`BEGIN IMMEDIATE`),
  включены `foreign_keys=ON`, конфликт занятости возвращает понятный ответ, а не
  сырую ошибку SQLite.
  Дефект: проверка занятости вне транзакции записи, гонка двух гостей на один
  слот, утечка деталей SQLite в ответ API.
- Проверять: целостность SQLite — `application_id` `0x43414c31`, `user_version`
  схемы, STRICT-таблицы, `PRAGMA journal_mode=DELETE`, `synchronous=EXTRA`,
  `foreign_keys=ON`, `busy_timeout=5000`, проверка `quick_check` при открытии,
  эксклюзивное создание нового файла и отказ открывать чужую или повреждённую
  базу сохраняются.
  Дефект: снятие любой из этих проверок без явного согласованного решения.
- Проверять: изменение схемы базы (новая версия после 3) допустимо только как
  безопасная миграция — в транзакции, с пошаговой проверкой фактической
  структуры (`checkSchema`) до и после каждого шага, с сохранением существующих
  данных, с `beforeMigrationCommit`-контролем при необходимости и с обновлёнными
  тестами миграции из версий 1, 2 и 3.
  Дефект: миграция вне транзакции, без сохранения данных, без проверки
  структуры или без тестов на существующих версиях; исчезновение возможности
  открыть базу прежней версии.

## 2. Контракт TypeSpec и производные

Область: `contract/main.tsp`, `contract/tspconfig.yaml`, производные файлы.

- Проверять: единственный исходник HTTP-контракта — `contract/main.tsp`; любое
  изменение контрактных данных внесено в TypeSpec, а цепочка
  TypeSpec → OpenAPI → производные перегенерирована командой
  `mise run api:generate`; изменённые производные сохранены в Git вместе с
  исходником.
  Дефект: изменение контракта правкой производных
  (`contract/openapi.json`, `contract/API.generated.md`, всего
  `contract/src/generated/`) вместо исходника.
- Проверять: ручное изменение генерируемых файлов отсутствует — diff
  производных соответствует перегенерации; `mise run api:check` зелёный.
  Дефект: ручная правка производных, отсутствие регенерации, расхождение
  `mise run api:check` с сохранёнными файлами.

## 4. Workflow-изменения: допуск, секреты, версии, права

Область: `.github/workflows/*.yml`, `scripts/prepare-github-agent.mjs`,
`scripts/verify-github-agent.mjs`.

- Проверять: допуск к секретам и checkout выполняется до раскрытия
  `OPENCODE_API_KEY`: проверяются репозиторий, автор (владелец `skaffman41`
  типа User и явно перечисленные доверенные боты), head и base ветки в этом
  репозитории; fork и недоверенные авторы отклоняются до checkout и секрета;
  код PR не выполняется в привилегированном контексте (без
  `pull_request_target` с выполнением кода PR).
  Дефект: секрет или доступный для записи checkout становятся доступными до
  решения о допуске; недоверенный код PR выполняется с секретами.
- Проверять: права заданий минимальны и перечислены явно (`contents: read`,
  `persist-credentials: false` у checkout, отдельные права только там, где есть
  конкретное обоснование в описании PR); токен агента не получает прав записи
  истории Actions.
  Дефект: расширение прав «на всякий случай», свободные credentials у checkout,
  право записи истории Actions у токена агента.
- Проверять: закреплённые версии сохраняются — opencode action и runtime
  1.19.6, модель `opencode/glm-5.3-flash-free` без платного fallback,
  `mise.lock`, `package-lock.json`, версии действий GitHub по закреплённым
  ссылкам. Обновление версии — отдельное согласованное решение, а не попутная
  правка.
  Дефект: переход на `latest`, плавающие теги, другая или платная модель
  без отдельного согласования.
- Проверять: у долгих заданий есть тайм-аут, у конкурентных (параллельных)
  запусков — явная concurrency-группа с обоснованным `cancel-in-progress`, а
  публикация комментариев и уведомлений выполняется отдельным шагом без вызова
  модели.
  Дефект: задание без тайм-аута, публикация из сессии модели, отмена работающего
  ответа без согласования.

## 5. Коммиты и документация

- Проверять: коммиты оформлены по Conventional Commits
  `type(scope): описание (#NN)` и каждый коммит реализации ссылается на свой
  тикет; снимок плана (`docs/plans/<feature>/vN/`) сохранён отдельным
  planning-коммитом до реализации.
  Дефект: коммит без ссылки на тикет, смешивание результатов нескольких тикетов
  в одном коммите, незакоммиченный или изменённый задним числом снимок плана.
- Проверять: документация соответствует изменённому поведению — README,
  `docs/agents/*`, `.github/workflows/README.md` обновлены там, где прежний
  текст становится неверным; календарная документация и `GLOSSARY.md` меняются
  только при реальном изменении терминов или поведения календаря.
  Дефект: несогласованная документация, документация, расширяющая полномочия
  запусков, и изменение терминов без следования `GLOSSARY.md`.
- Проверять: все ссылки и пути в новых и изменённых документах корректны
  (якоря существуют, пути ведут к реальным файлам), Prettier и линтер зелёные,
  `git diff --check` чистый.
  Дефект: битые ссылки и якоря, пути к несуществующим файлам, невыполненная
  проверка форматирования.
- Проверять: локально проверенное отделено от живой приёмки — в описании PR и
  отчётах явно указано, какие проверки выполнены (команды, SHA, ссылки на runs),
  а какие остаются живой приёмкой владельца после merge.
  Дефект: выдача локально подготовленного за подтверждённое живое поведение.
