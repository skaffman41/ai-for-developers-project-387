## Parent

Спецификация [#53 «Регулярный аудит зависимостей GitHub-агентом — шаг 5 Hexlet»](https://github.com/skaffman41/ai-for-developers-project-387/issues/53). Вторая задача согласованного линейного графа.

## What to build

Владелец получает полный сценарий «аудит → анализ и поиск существующих Issues → максимум одна новая задача по существенной находке → журнал со связями». Тем же workflow можно повторно обработать сохранённый отчёт и показать отсутствие дублей, а при отсутствии подходящей реальной находки — явно учебный пример.

Самостоятельный результат — автоматическое создание конкретной входящей задачи и воспроизводимый повтор без второй задачи по той же проблеме. Сбор реального отчёта и постоянный журнал из блокирующего тикета сохраняются; исправление зависимостей и PR по находкам не выполняются.

## Acceptance criteria

- [ ] Агент анализирует отчёт и существующие открытые/закрытые Issues; по наиболее серьёзной ещё не зарегистрированной high/critical автоматически создаётся не более одного отдельного Issue за запуск. Low/moderate не создают отдельные задачи; остальные данные остаются в отчёте и сводке.
- [ ] Issue содержит конкретную проблему, пакет/advisory, серьёзность, сведения о проверенном репозитории и SHA, предлагаемое действие, применимость/ограничения, связь с отчётом и ссылку на run. Advisory не выдаётся за доказанный дефект календаря; рискованное принудительное обновление не предлагается как обязательное универсальное решение.
- [ ] Новая задача остаётся входящим обращением: реализация, автоматическая готовность к реализации, изменение кода, исправляющий PR и merge не запускаются.
- [ ] Дубль определяется стабильной парой «пакет + advisory», а не текстом модели, временем или хешем всего отчёта. Идентичность сохраняется в задаче; полный поиск использует пагинацию открытых и закрытых Issues и исключает PR из числа задач.
- [ ] При существующей открытой либо закрытой задаче новая задача, одинаковый комментарий и автоматическое переоткрытие не выполняются. Журнал содержит ссылку на найденную задачу и не скрывает текущие сведения отчёта. При нескольких находках выбирается ещё не зарегистрированная.
- [ ] Перед фактическим созданием проверяется наличие задачи; общий предел и сериализация запусков сохраняются. Повтор после успешного создания задачи и последующего отказа обновления журнала не создаёт второй Issue по той же находке.
- [ ] Ручной запуск того же workflow может обрабатывать те же байты сохранённого отчёта. Проверяются доступность и идентичность источника; исходные SHA и тип данных остаются явными. Повтор не выдаётся за свежий запрос registry или за проверку нового SHA.
- [ ] Для демонстрации при отсутствии подходящей новой реальной находки предусмотрен явно учебный вход с подготовленной находкой. Отчёт, журнал и созданная задача обозначены учебными и не утверждают наличие выдуманного дефекта приложения. Учебная идентичность отделена от реальной.
- [ ] Сохранённые реальные и учебные отчёты, результаты анализа и диагностика не попадают в Git. Повтор использует проверяемый сохранённый источник, а не заново собранный предположительно похожий JSON.
- [ ] Постоянный журнал связывает результат с созданной/известной задачей, сохраняет все согласованные статусы и обновляется без повторных одинаковых комментариев. Ошибка данных/модели/публикации не выдаётся за успешную приёмку.
- [ ] Руководство описывает порог и лимит задач, идентичность и поиск дублей, повтор исходного отчёта, учебный режим и границы автоматизации.
- [ ] Согласованные автоматические проверки, независимые Standards/Spec и полный mise run check успешны. Возможности первого тикета и неизменность workflow Hexlet сохранены.

## Testing Decisions

Новые проверки прямо разрешены Testing Decisions #53. Через тот же высокий шов audit-runner проверить реальные по форме и искусственные входные данные с управляемыми npm/model/GitHub-границами: новая high/critical, несколько кандидатов и лимит одной задачи, low/moderate без новой задачи, существующий открытый/закрытый Issue, пагинация, PR в inventory, изменившаяся формулировка модели, повтор точных данных, частично успешная публикация и повтор после неё, ошибочный/недоступный сохранённый источник, учебная маркировка и отсутствие смешения с реальными Issues.

Проверять наблюдаемые операции создания/обновления и сохранённые результаты, а не только вычисление внутреннего ключа. Новые проверки включаются в существующий общий check. Реальное создание Issue и повтор в Actions остаются обязательными доказательствами третьего тикета.
