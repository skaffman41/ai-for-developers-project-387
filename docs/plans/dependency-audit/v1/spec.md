## Problem Statement

Владелец репозитория «Календарь звонков» узнаёт о проблемах зависимостей только при ручной проверке. Нужен регулярный процесс, который получает проверяемые данные, поручает GitHub-агенту их анализ и превращает новую существенную находку в конкретное входящее обращение, не создавая дубли и не начиная исправления без решения человека.

Результат должен выполнять **все обязательные требования и все семь задач [шага 5 Hexlet «Регулярные задачи по расписанию»](https://ru.hexlet.io/projects/387/members/54793?step=5)**. Наличие YAML, локальная проверка или утверждение агента без живых доказательств не завершают шаг.

## Solution

Один workflow GitHub Actions ежедневно в 06:17 по Москве и по ручному запуску из основной ветки получает полный JSON-отчёт npm audit по зависимостям проекта. Агент получает явный prompt, анализирует отчёт, рассматривает существующие открытые и закрытые Issues и формулирует результат. По новой проблеме уровня high или critical автоматически создаётся не более одного отдельного Issue за запуск. Остальные находки сохраняются в отчёте и учитываются в сводке.

Содержательный последний вывод хранится в одном постоянном Issue журнала аудита; исходные данные и диагностические материалы — в артефактах Actions. Повторная обработка того же отчёта не создаёт повторных задач или одинаковых комментариев. Исправление найденных проблем остаётся отдельным решением человека.

Подготовка выполняется локальным агентом. Рабочий анализ и публикация результатов выполняются в GitHub Actions без команды /oc. Приёмка включает успешный ручной запуск того же workflow из main, автоматическое создание отдельной задачи и повтор с теми же исходными данными. Если подходящих реальных находок нет, демонстрация использует явно обозначенный учебный отчёт и учебную задачу.

## Implementation Decisions

1. **Предмет аудита.** Используется npm audit в JSON-режиме по существующему lockfile всех workspaces, включая зависимости разработки. Lighthouse и публичный адрес приложения для выбранного варианта не требуются. Собирается полный отчёт; порог high/critical применяется к созданию задач, а не к сохранению исходных данных. Автоматическое исправление зависимостей не выполняется.
2. **Расписание и входы.** Один файл workflow содержит schedule и workflow_dispatch. Расписание — один запуск в сутки в 06:17 Europe/Moscow. Рабочий запуск разрешён из main; выбор другого ref при ручном запуске не должен обходить это ограничение. Запуск по расписанию может задержаться средствами GitHub, поэтому приёмка не требует ожидания ночного события.
3. **Ограничение выполнения.** Тайм-аут аудита — 20 минут. Расписание и ручные запуски используют общую concurrency-группу: одновременно выполняется один аудит, работающий запуск не отменяется новым аудитом. Финальная публикация результата получает возможность отработать после ошибки анализа в пределах явно ограниченного времени.
4. **Происхождение данных.** Результат содержит репозиторий, исследованный SHA основной ветки, идентичность lockfile/отчёта, тип данных (реальные или учебные), ссылку на Actions run и итог. При повторной обработке сохранённого отчёта исходная версия данных остаётся явной: повтор не выдаётся за свежий запрос к registry или за аудит иной версии приложения.
5. **Вход агента.** Агент получает фиксированный prompt, исходный отчёт и контекст существующих Issues, включая закрытые записи. Он анализирует применимость находок и ищет уже зарегистрированные проблемы. Данные отчёта и тексты Issues не могут расширять разрешённые операции агента. Пользовательский комментарий и команда /oc для этого входа не нужны.
6. **Модель и инструменты.** Повторно используются действующие закреплённые OpenCode CLI 1.19.6, бесплатная модель opencode/deepseek-v4.1-flash-free и подготовка Matt Pocock Skills. Пример существующего независимого CLI-ревью служит основой, но новый сценарий не зависит от наличия PR или события комментария. Точная версия CLI проверяется; закрепление action само по себе не подменяет закрепление устанавливаемого runtime. Недоступность бесплатной модели не включает платный fallback.
7. **Авторизация.** Для сценария чтения репозитория и публикации Issues достаточно минимальных прав чтения кода и записи Issues через токен Actions. Права изменения кода, создания PR, merge и изменения истории Actions аудиту не нужны. Публикация ограничивается согласованным репозиторием, одним журналом и задачами по находкам. Существующие ограничения других режимов GitHub-агента сохраняются; новый режим явно описывается в инструкциях.
8. **Отбор задач.** Не более одного нового Issue по находке за запуск. Выбирается наиболее серьёзная ещё не зарегистрированная проблема high/critical. Остальные находки остаются в исходном отчёте и отражаются в сводке. Отсутствие исправления без риска само по себе не основание советовать принудительное обновление: предлагаемым действием может быть отдельная проверка применимости или подготовка безопасного обновления.
9. **Идентичность и дубли.** Одна проблема определяется стабильной парой «имя затронутого пакета + идентификатор advisory». Идентичность не зависит от текста модели, времени запуска или хеша всего отчёта. Проверяется полный доступный набор открытых и закрытых Issues с пагинацией, без подмены Issues пуллреквестами. Соответствующий маркер сохраняется в созданной задаче. Перед фактическим созданием выполняется проверка наличия задачи; повтор после частичной публикации не должен создавать второй Issue.
10. **Известные и закрытые задачи.** По уже известной проблеме новая задача, одинаковый комментарий или автоматическое переоткрытие не выполняются. В журнале сохраняются ссылка на найденную задачу и текущие сведения отчёта. Новые сведения не скрываются, но расширенный сценарий автоматического ведения повторно появившейся исправленной проблемы не входит в этот объём.
11. **Задача по находке.** Отдельный Issue содержит проблему, пакет/advisory и серьёзность, сведения о проверенном проекте и версии, предлагаемое действие, обоснование применимости или её ограничения, ссылку на прогон и источник отчёта. Он остаётся входящим обращением: аудит не объявляет его автоматически готовым к реализации и не запускает исправление. Известный advisory не выдаётся за подтверждённый дефект календарной функциональности.
12. **Постоянный журнал.** На процесс существует один служебный Issue журнала, отличимый от задач по находкам. Его тело обновляется последним результатом без повторных одинаковых комментариев. Лимит одной новой задачи по находке не мешает первоначальной подготовке единственного журнала. Журнал содержит содержательное заключение агента, ссылки на новые/известные задачи, SHA, тип и идентичность данных и ссылку на запуск; одной ссылки на временный артефакт недостаточно.
13. **Результаты и ошибки.** Различаются: полностью чистый отчёт; находки ниже выбранного порога; известные high/critical; новая high/critical; ошибка получения отчёта; ошибка или тайм-аут модели; ошибка публикации. Ненулевой exit npm audit при наличии валидного отчёта с advisories не считается автоматически технической ошибкой. Невалидный/недоступный отчёт или результат модели не преобразуется в вывод «проблем нет» и не подтверждает исправление ранее известной проблемы.
14. **Отчёты и повтор.** Исходный JSON, машинный результат анализа и доступная диагностика сохраняются артефактами Actions с явно описанным сроком хранения. Временные материалы лежат вне рабочего дерева либо в игнорируемом каталоге и не включаются в коммиты. Для повторной приёмки предусмотрена обработка того же сохранённого отчёта с проверяемой идентичностью. Повтор не создаёт новые findings только из-за изменившегося текста ответа модели.
15. **Учебные данные.** Когда подходящей новой реальной находки нет, тот же workflow допускает явно обозначенную учебную проверку с подготовленной находкой. Журнал, отчёт и созданная задача маркируют учебный характер; она не считается доказанным дефектом приложения. Учебная идентичность отделена от реальных задач. Полученные учебные отчёты также не коммитятся.
16. **Документация.** Руководство проекта описывает цель и границы аудита, расписание, ручной запуск и повтор, права, отчёты и постоянный журнал, порог/лимит задач, результаты реальных прогонов и ограничения. Личные выводы принадлежат владельцу: после живых прогонов текст обсуждается с ним, а агент не придумывает его мнение. В нём отражаются потребовавшие уточнений условия и изменения настроек или постановки задачи.
17. **Изменение проекта.** Календарная функциональность, HTTP-контракт, данные бронирований и существующие режимы GitHub-агента не меняются. Обязательная проверка Hexlet сохраняется побайтно. Планирование, локальная реализация и публикация остаются отдельными стадиями; push, PR, merge и включение workflow в основную ветку требуют предусмотренных проектом отдельных команд.

## Testing Decisions

Новые автоматические проверки механизма аудита **прямо разрешены владельцем** в обсуждении grill-with-docs: вопрос Q7 и ответ «Все — да, если это соответствует задачам и требованиям из условия шага». Повторного согласования тех же швов не требуется.

Хорошая проверка оценивает внешнее поведение: какие данные прочитаны, какое заключение сохранено, какие обращения предложены/созданы и что произошло при повторе. Она не повторяет внутренние функции реализации и не зависит от текущего списка advisories или доступности бесплатной модели.

1. **Основной автоматический шов — процесс аудита целиком.** Заданные исходный отчёт, inventory Issues и управляемые ответы внешних границ приводят к проверяемым результатам анализа, операциям публикации и журналу. Используются существующие Vitest-подходы проекта к дочерним процессам, временному окружению и подмене внешних CLI; календарные HTTP/E2E-наборы не превращаются в новый шов аудита.
2. **Сбор и валидация.** Проверяются чистый отчёт, advisory с ожидаемым ненулевым exit, несколько уровней серьёзности, включение зависимостей разработки, невалидный JSON и технический отказ получения данных. Ни один отказ не выдаётся за чистый аудит.
3. **Отбор и содержание.** Проверяются новая high/critical и предложенное действие, отчёт только с low/moderate без новой задачи, сохранение остальных находок и лимит одной новой задачи по наиболее существенной незарегистрированной проблеме. Проверяются сведения о происхождении и явные ограничения применимости.
4. **Дубли.** Повтор того же отчёта, другая формулировка модели, уже открытая и уже закрытая задача, несколько страниц inventory и наличие PR не приводят к повторной задаче. Стабильный ключ сохраняется; повтор после частично успешной публикации учитывает уже созданный результат.
5. **Журнал.** Повторные запуски используют один журнал и обновляют его тело без одинаковых комментариев. В нём остаётся содержательный вывод, а не только ссылка на артефакт. Реальные и учебные результаты различимы.
6. **Модель и публикация.** Проверяются некорректный ответ, ошибка/тайм-аут модели, отсутствие конфигурации, отказ GitHub и невозможность произвольной публикации вне согласованных операций. Повторные вызовы не обходят лимит и поиск дублей. Платная модель или запись кода не включаются как запасной путь.
7. **Workflow и подготовка.** Проверяются оба события в одном файле, ограничение main, расписание не чаще раза в сутки, тайм-аут, общая concurrency, prompt, минимальные права, закрепление runtime/model и сохранение отчётов вне коммитов. Это дополняет поведенческие проверки и не заменяет живую приёмку.
8. **Prior art.** Существующие suites pr-review-bootstrap, pr-review-helpers, pr-review-output, pr-review-workflow, opencode-budget-workflow и opencode-reporter-workflow показывают подготовку CLI, контроль входов, результат модели, публикацию и проверку YAML. Их подходы переиспользуются там, где это уменьшает число новых границ.
9. **Проверки реализации.** Для существенной реализации нужны независимые Standards и Spec, профильные проверки и полный существующий mise run check. Сохраняется неизменность workflow Hexlet. На стадии одной публикации спецификации реализационные тесты не запускаются.
10. **Живая приёмка — отдельный обязательный шов.** После отдельно разрешённой интеграции workflow в main подтверждаются его включённость и расписание; выполняется успешный ручной запуск из main с реальным вызовом модели, артефактом и постоянным выводом. Агент автоматически создаёт отдельную задачу по подходящей новой находке либо по явно учебному отчёту. Следующий ручной запуск обрабатывает те же байты исходного отчёта; сравниваются ключи находки, созданные задачи, журнал и список комментариев. Нового дубля нет. Оба прогона имеют ссылки, SHA и результаты; ждать фактического запуска по расписанию для сдачи не нужно.

## Out of Scope

- Lighthouse, аудит скорости/доступности страниц, новая публичная выкладка, APP_URL и изменение исторического стенда проекта 386.
- Частота расписания чаще одного запуска в сутки, платная модель и платный fallback.
- Автоматическое переоткрытие закрытых Issues и дополнительное задание о повторном появлении исправленной проблемы со связью с исправляющим PR.
- Универсальный runtime implement-spec и отложенный граф #41–#49.
- Изменение правил календаря, схемы хранения бронирований, API-контракта и workflow Hexlet.
- Переписывание опубликованной истории, старых снимков планов или существующих отчётов.
- Самостоятельное прохождение кнопок завершения и сдачи проекта на Hexlet от имени владельца.

## Further Notes

### Согласование и границы стадии

Спецификация синтезирована из текущего обсуждения grill-with-docs по шагу 5. Владелец подтвердил Q1–Q3 ответом «Все — да», затем Q4–Q7 ответом «Все — да, если это соответствует задачам и требованиям из условия шага». Последующее уточнение закрепило выполнение каждого обязательного пункта, а не только подготовку workflow. Команда $to-spec отдельно разрешает публикацию этой спецификации в каноническом трекере.

Подготовка выполняется локально; рабочий агент и приёмка — в GitHub Actions. /oc может использоваться человеком для других согласованных задач, но не является обязательным вызовом для расписания. Приёмку нельзя объявить выполненной до живых прогонов из main и внесения результатов/личных выводов в README.md.

Исследованная база — main 14393bb14808a899e6f9c3969442db21173ff394 репозитория skaffman41/ai-for-developers-project-387. Готового периодического аудита в ней нет. Существующий обычный обработчик GitHub-комментариев ожидает event.comment; его нельзя без отдельной адаптации считать готовым для schedule. Публичный стенд Railway относится к проекту 386 и не нужен этому аудиту.

На этой стадии публикуется только спецификация. Native sub-issues, блокеры и полный неизменяемый planning snapshot с manifest создаются после согласования графа через $to-tickets; отдельный planning-коммит должен предшествовать реализации. Метка ready-for-agent не означает выполненные критерии и не разрешает публикацию кода или merge.

### Критерии приёмки

- [ ] **AC1.** В main находится один audit-workflow с schedule и workflow_dispatch; workflow включён. Указан ежедневный запуск 06:17 Europe/Moscow, частота не больше раза в сутки, тайм-аут 20 минут и общая concurrency для ручного и планового запусков.
- [ ] **AC2.** Оба входа запускают согласованный аудит из main с явным prompt и необходимыми правами. /oc и контекст комментария не требуются. Модель/CLI закреплены; платного fallback и полномочий изменения кода/PR у аудита нет.
- [ ] **AC3.** Реальный источник — npm audit по полному закреплённому дереву зависимостей, включая devDependencies. Исходный JSON сохранён целиком; происхождение отчёта, исследованный SHA и идентичность данных доступны.
- [ ] **AC4.** Агент анализирует отчёт, применимость и существующие открытые/закрытые Issues, сохраняет содержательный вывод. Полностью чистый отчёт, отсутствие новых high/critical, известные проблемы и техническая ошибка различаются.
- [ ] **AC5.** Агент автоматически создал отдельный Issue по конкретной новой high/critical: проблема, предлагаемое действие, пакет/advisory, версия проекта, связь с отчётом и run. Если подходящей реальной находки нет, этот результат показан на явно учебном отчёте с учебным Issue, без объявления выдуманного дефекта приложения.
- [ ] **AC6.** За запуск появляется не более одной новой задачи по находке; остальные данные не теряются. Новая задача остаётся входящей и не запускает реализацию.
- [ ] **AC7.** Повтор тех же исходных данных не создаёт дубля задачи или одинакового комментария; учитываются открытые/закрытые Issues и стабильная идентичность пакета/advisory. Повтор после частичной публикации также не создаёт второй Issue по той же находке.
- [ ] **AC8.** Есть один постоянный Issue журнала с последним содержательным выводом, ссылками на новые/известные задачи и Actions run, SHA, происхождением/типом данных. Обновляется тело журнала; вывод не сводится к временной ссылке и не исчезает вместе с артефактом.
- [ ] **AC9.** Сбор данных, модель и публикация имеют проверяемые результаты ошибок; отсутствие отчёта/модели не выдаётся за чистоту или исправление. Отчёты сохраняются артефактами с описанным сроком хранения и не попадают в Git, включая учебные результаты.
- [ ] **AC10.** Согласованные автоматические проверки проходят; для существенной реализации успешны независимые Standards/Spec и полный mise run check. .github/workflows/hexlet-check.yml не изменён.
- [ ] **AC11.** Есть успешный ручной запуск того же workflow из main с вызовом модели, сохранённым отчётом, доступным заключением и созданным Issue; есть второй прогон на тех же данных без дублей. Сохранены прямые ссылки на оба запуска, отчёт/идентичность данных, задачу и журнал. Одного локального прогона или YAML недостаточно.
- [ ] **AC12.** README.md описывает workflow, расписание, ручной запуск и повтор, права/границы, результаты и места хранения, прямые ссылки на приёмку; в нём либо связанном документе опубликованы согласованные с владельцем личные выводы: что требовало уточнений и что изменили в настройках или постановке задачи.
