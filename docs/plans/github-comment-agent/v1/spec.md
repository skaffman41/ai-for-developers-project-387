## Problem Statement

В проекте «Календарь звонков (продолжение)» локальный агент уже использует согласованные правила работы и GitHub Issues, но агент в GitHub ещё не подключён. Владелец репозитория не может вызвать его из обсуждения, получить ответ от приложения и отдельно поручить публикацию небольшой правки. Существующие проверки приложения не обеспечивают такой сценарий и не подтверждают доступность локальных глобальных скиллов на чистом раннере.

Нужно выполнить все восемь пунктов блока «Требования» шага 2 Hexlet и подтвердить результат реальными ответами и прогонами. Для учебного проекта нужны бесплатная модель, отсутствие дополнительных личных расходов и явная граница между вопросом агенту и разрешением публиковать код.

## Solution

Подключить официальный OpenCode GitHub App к репозиторию `skaffman41/ai-for-developers-project-387` и подготовить workflow вызова агента из комментариев к Issues и PR, включая комментарии к строкам diff. Вызов доступен только аккаунту `skaffman41` через `/oc` и `/opencode`; комментарии ботов, неподходящие события и недоверенные PR из fork не получают доступ к вызову модели и её секрету.

Обычное обращение допускает чтение и ответ. Отдельная команда `/oc publish <задача>` разрешает изменение файлов, push рабочей ветки и создание либо обновление PR. Длинная форма `/opencode` эквивалентна короткой. Merge требует отдельной команды.

Свежий раннер получает закреплённые скиллы первого проекта и актуальные настройки трекера проекта 387. Выбирается бесплатная модель `opencode/glm-5.3-flash-free`, публикация сессий отключается. Результат приёмки связывает каждый пункт требований Hexlet с проверяемым свидетельством; два живых сценария подтверждают ответ в Issue и отдельно разрешённую публикацию правки README.

## Implementation Decisions

1. Целевой репозиторий и текущий трекер — `skaffman41/ai-for-developers-project-387`; основная ветка — `main`. Исходный проект 386 сохраняет роль исторического источника, его существующие планы и номера не переопределяются.
2. Используется официальный OpenCode GitHub App и стандартный GitHub-адаптер. Собственное приложение, fork адаптера и другой агент не входят в принятое решение.
3. Workflow обрабатывает только `issue_comment` и `pull_request_review_comment` с `types: [created]`. Допуск к вызову модели требует стандартной команды, точного аккаунта `skaffman41` и автора, который не является ботом. Само наличие комментария не означает вызова модели.
4. Вызовы и подготовка окружения не должны передавать секрет модели недоверенному коду PR из fork. Не применяется выполнение такого кода через `pull_request_target`.
5. Для стандартной авторизации задаются `contents: read`, `id-token: write` и `persist-credentials: false` у checkout. Комментарии и разрешённая публикация выполняются правами GitHub App. Более широкие права должны иметь конкретное обоснование; изменение способа авторизации требует согласования.
6. Набор `mentions` явно фиксирует `/oc` и `/opencode`; обе формы эквивалентны. Настройка `share: false` задаётся явно и отражается в пользовательском описании интеграции.
7. Обычный режим разрешает только чтение и ответ. Он должен исключать изменение файлов и публикацию ветки или PR. Это обеспечивается эффективными разрешениями инструментов и чистотой рабочей копии, включая подготовку окружения; одних инструкций модели недостаточно, поскольку финализатор стандартного адаптера публикует найденные изменения самостоятельно.
8. Команда `/oc publish <задача>` является явным разрешением на изменение файлов, push рабочей ветки и создание либо обновление PR для указанной задачи. Длинная форма вызова имеет ту же семантику. Разрешение не распространяется на merge, другие репозитории, произвольные задачи и последующие обращения.
9. Режим публикации сохраняет требования к согласованному плану, коммитам, проверкам и ревью; команда публикации не отменяет их. Обычные локальные режимы работы сохраняют прежние границы полномочий.
10. Выбрана бесплатная модель `opencode/glm-5.3-flash-free`, без использования учебного бюджета и дополнительных личных расходов. Её доступность, нулевая стоимость и совместимость с выбранным GitHub runtime проверяются до приёмки. Недоступность, исчерпание квоты и отмена бесплатности приводят к понятному незавершённому результату, без автоматического перехода на платную модель. Другая модель требует отдельного решения.
11. Ключ провайдера хранится только в GitHub Actions Secrets; для выбранного провайдера используется секрет `OPENCODE_API_KEY`. Его значение не публикуется и не сохраняется в коде. Подготовка ключа и установка приложения требуют участия человека через штатные интерфейсы сервисов.
12. Предел одного задания — 30 минут. На один Issue или PR допускается не более одного активного запуска; комментарии разных типов к одному PR относятся к одной области concurrency. Новый комментарий не отменяет активный запуск автоматически.
13. Раннер явно подготавливает тот же набор Matt Pocock Skills, который закреплён в проекте: 38 скиллов из согласованной ревизии с проверкой состава и содержимого по существующему lock. Подготовка должна учитывать обнаружение скиллов именно OpenCode; наличие папок само по себе не доказывает, что агент может их прочитать.
14. Агент получает актуальные проектные инструкции и настройки GitHub Issues. Обязательно доступны `to-spec`, `to-tickets` и `implement-spec`, правильное имя текущего трекера и команда общей проверки. Исторические свидетельства проекта 386 не выдаются за результат запуска в 387.
15. Версии action и runtime закрепляются и проверяются вместе. Исследование выявило различие поколений локального OpenCode и стандартного GitHub-адаптера; примеры конфигурации одного поколения нельзя считать доказательством работы другого. Конкретный поддерживаемый способ ограничения инструментов выбирается и проверяется при реализации без изменения согласованного поведения.
16. Изменяются интеграция GitHub-агента, подготовка раннера и описание его использования. Проектные инструкции дополняются только там, где нужно отразить GitHub-режим; актуальные команды разработки сохраняются. Обязательный workflow Hexlet остаётся побайтно неизменным.
17. Завершение требует включения workflow в основную ветку и живых свидетельств. Локально подготовленная конфигурация, успешный синтаксический анализ или факт установки App сами по себе не завершают шаг.

## Testing Decisions

1. Согласованная основная граница проверки — внешний сценарий «комментарий пользователя → GitHub Actions → ответ приложения или разрешённые изменения и PR». Проверяется наблюдаемое поведение, а не устройство внутренних функций адаптера или совпадение реализации с её собственными тестовыми ожиданиями. Пользователь подтвердил два живых прогона при обсуждении замысла.
2. Первый прогон выполняется на свежем раннере по обычной команде в Issue. Агент читает проектные настройки и скиллы, правильно называет GitHub Issues проекта 387, доступные `to-spec`, `to-tickets`, `implement-spec` и `mise run check`, отвечает в обсуждении от имени приложения. Сохраняются ссылки на команду, ответ и успешный Actions run.
3. Первый прогон также подтверждает режим чтения: подготовка и ответ не оставляют изменений, способных запустить автоматическую публикацию адаптером; ветка или PR с изменениями не публикуются. Эффективные разрешения инструментов проверяются в выбранном runtime, включая запрет путей обхода через запись, shell и делегирование.
4. Второй прогон запускается отдельной явной командой публикации для небольшой правки README. Он должен дать ожидаемую правку, push рабочей ветки и созданный либо обновлённый PR без автоматического merge. Проверяется, что существующие обязательные проверки применимы и успешны; свидетельства связываются с конкретным SHA.
5. На границе workflow проверяются оба типа комментариев, ограничение на созданные события, точный доверенный автор, игнорирование ботов, защита fork, права, отсутствие сохранённых checkout credentials, явные mentions/share, тайм-аут и общая concurrency для одного Issue/PR. Используются разбор конфигурации, проверка эффективных настроек и доступная история Actions; наличие неподтверждённого сценария отмечается явно.
6. Проверяются фактическая доступность бесплатной модели и работа с инструментами в GitHub runtime, а также понятный результат при ошибке модели/квоты и отсутствие платного fallback. Успешный вызов другой модели не заменяет приёмку выбранной модели.
7. Для подготовки окружения проверяются закреплённый состав скиллов, возможность их обнаружить и прочитать из OpenCode и использование текущего трекера. Предшествующий пример — сохранённая в проекте проверка GitHub Issues workflow со свежим сеансом, проверкой скиллов и матрицей свидетельств; это исторический образец подхода, а не готовое доказательство нового результата.
8. Применяются существующий `mise run check`, проверки YAML/форматирования, ссылок и diff. Существующие Vitest и Playwright остаются проверками приложения; они не подменяют живую проверку интеграции GitHub-агента.
9. Новые файлы автотестов и расширение набора автотестов этим планом не поручаются. При необходимости такого расширения требуется отдельный прямой запрос пользователя. Разовые проверки конфигурации и два согласованных живых прогона оформляются как свидетельства приёмки.

## Out of Scope

- Изменение бизнес-поведения «Календаря звонков», HTTP-контракта, схемы данных и опубликованного стенда.
- Платные модели, расходование учебного бюджета, добавление платёжной карты и автоматический переход на другую модель.
- Вызовы модели по расписанию, при каждом PR, при открытии Issue и от других пользователей или ботов.
- Публикация сессий OpenCode и передача секретов недоверенным fork.
- Автоматический merge, обход проверок и изменение обязательного workflow Hexlet.
- Собственное GitHub App, fork стандартного адаптера, новая платформа агента или неподтверждённая замена способа авторизации.
- Проверка полного выполнения будущих спецификаций через `implement-spec`: на этом шаге подтверждаются доступность скилла и настройки окружения, а не реализация следующей функциональности календаря.
- Создание графа задач реализации и старт реализации в рамках команды `to-spec`; это следующие стадии согласованного workflow.
- Новые автотесты без отдельного прямого запроса.

| AC-08 | Агент ответил на команду в Issue, прогон виден в Actions.                                                                                                 | Доступны команда владельца, содержательный ответ приложения и связанный успешный Actions run в проекте 387.                                                                                                   |

Дополнительные согласованные критерии: обычный запрос не публикует изменения; `/oc publish` даёт проверяемую правку README и PR; сессии не публикуются; выбранная модель действительно бесплатна и работает в закреплённом GitHub runtime; все существующие обязательные проверки сохранены. Шаг не принимается при невыполненном пункте AC-01–AC-08, даже если демонстрационный ответ получен.
