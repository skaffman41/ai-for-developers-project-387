## Parent

[Спецификация #3: Подключить OpenCode к GitHub Actions по команде владельца — шаг 2 Hexlet](https://github.com/skaffman41/ai-for-developers-project-387/issues/3)

## What to build

Довести подготовленную интеграцию до проверенного результата шага 2 Hexlet: установить официальный App на проект 387, подготовить ключ бесплатной модели через штатные интерфейсы, включить проверенный workflow в основную ветку по отдельным явным командам и провести два согласованных живых сценария. Владелец получает ответ приложения в Issue, затем по отдельной команде — небольшую правку README и PR. Отчёт связывает каждый пункт блока «Требования» с конкретным свидетельством.

Действия, требующие человека, заранее подготовлены так, чтобы он подтверждал конкретный результат. Задача не отменяет обязательные отдельные разрешения на push, создание PR и merge; отсутствие необходимого разрешения или доступа отражается как незавершённый результат.

## Acceptance criteria

- [ ] AC-01: официальный OpenCode GitHub App установлен на целевой репозиторий 387; работа выбранной авторизации подтверждена реальным запуском.
- [ ] AC-02: проверенный workflow присутствует в `main`; свежий раннер подготавливает тот же закреплённый набор скиллов и актуальные настройки GitHub Issues. Есть доказательства состава скиллов и их чтения агентом.
- [ ] AC-03: проверены оба события, ограничение `created`, точный доверенный автор, игнорирование ботов и отсутствие доступа недоверенных fork к секрету. Зафиксированы выполненные проверки и их границы; неподтверждённые условия не объявлены пройденными.
- [ ] AC-04: в опубликованной конфигурации сохранены `contents: read`, `id-token: write`, `persist-credentials: false`; ответ приложения и отдельно разрешённая публикация подтверждают работоспособность авторизации.
- [ ] AC-05: ключ выбранного провайдера добавлен только в Actions Secrets без раскрытия значения в отчётах или коде; успешный вызов подтверждает пригодность ключа. Реальный workflow содержит предел 30 минут и согласованную concurrency.
- [ ] AC-06: актуальный README описывает оба события, назначение, выбранную бесплатную модель, обычный режим и публикацию, оба mentions, `share: false` и место просмотра результатов. В отчёте есть ссылки на реальные результаты.
- [ ] AC-07: команды в AGENTS.md сверены с действующей конфигурацией проекта; GitHub-режим соответствует согласованной границе публикации.
- [ ] AC-08: получен содержательный ответ приложения на команду владельца в Issue и связанный успешный Actions run; агент правильно называет текущий трекер, доступные `to-spec`, `to-tickets`, `implement-spec` и `mise run check`.
- [ ] Первый живой прогон подтвердил обычный режим: агент прочитал настройки и скиллы, ответил в обсуждении и не опубликовал изменений, ветки или PR с правками.
- [ ] Второй живой прогон выполнен отдельной командой `publish`: получены ожидаемая небольшая правка README, push рабочей ветки и созданный либо обновлённый PR. Автоматического merge не было; существующие обязательные проверки успешны и связаны с конкретным SHA.
- [ ] В реальном GitHub runtime работает именно `opencode/glm-5.3-flash-free` с инструментами; бесплатность проверена на момент запуска. Смена модели, платный fallback и расходование учебного бюджета не применялись. Ошибки модели или квоты дают понятный незавершённый результат; невозможность доказать обязательный сценарий не заменяется заявлением об успехе.
- [ ] Сессии OpenCode не опубликованы, значение ключа не раскрыто; существующий workflow Hexlet сохранён побайтно, обязательные проверки не отключались.
- [ ] Итоговая матрица содержит отдельное свидетельство по AC-01–AC-08, ссылки на команды, ответы, Actions, PR и соответствующие SHA, результаты проверок и ревью, а также существенные ограничения.
- [ ] Итог не объявлен принятым при невыполненном критерии родительской спецификации. Код и отчёт оформлены по проектному workflow; родительская спецификация не закрывается автоматически этой задачей.

## Testing Decisions

Выполняются два согласованных внешних сценария спецификации #3: «комментарий → свежий Actions runner → ответ» и «отдельная команда публикации → правка → push → PR». Проверяются фактические результаты, а не только наличие конфигурации. Исторические результаты проекта 386 и локальные проверки предшествующих задач не заменяют живые свидетельства проекта 387. Используются существующие проверки проекта, анализ конфигурации и истории Actions; новые автотесты не добавляются. Необходимые действия человека подготавливаются и выполняются через штатные интерфейсы с требуемыми разрешениями.
