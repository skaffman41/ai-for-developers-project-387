## What to build

Подготовить сквозной путь обычной команды владельца репозитория: подходящий комментарий допускается к запуску, свежая среда получает закреплённые скиллы и настройки проекта 387, OpenCode читает проект и формирует ответ без разрешения менять файлы или публиковать изменения. Workflow, подготовка среды, ограничения инструментов и описание использования образуют один проверяемый результат.

В этой задаче проверяются подготовленный workflow и эффективная конфигурация закреплённого runtime без установки GitHub App и передачи ключа модели. Реальный ответ приложения и совместимость бесплатной модели с полным GitHub-запуском подтверждаются финальной задачей живой приёмки; их нельзя объявлять уже выполненными.

## Acceptance criteria

- [ ] Подготовлен workflow официального OpenCode GitHub App для новых `issue_comment` и `pull_request_review_comment`; обычные команды `/oc` и `/opencode` эквивалентны.
- [ ] До доступа к секрету и вызову модели проверяются точный аккаунт `skaffman41`, тип автора, подходящая команда и доверенность контекста PR. Боты и неподходящие события не вызывают модель; недоверенный код fork не получает секрет. `pull_request_target` для его исполнения не применяется.
- [ ] Стандартная авторизация сохраняет `contents: read`, `id-token: write` и `persist-credentials: false`; ключ ожидается только из Actions Secrets, его значение не нужно для подготовки и не попадает в код или журналы.
- [ ] Версии action и runtime закреплены совместно. Эффективная конфигурация обычного режима разрешает чтение и ответ, запрещает изменение файлов и обход запрета через shell или делегирование; проверка выполнена средствами выбранного runtime, а не только чтением prompt.
- [ ] Подготовка окружения не оставляет изменений в рабочей копии, которые автоматический финализатор адаптера мог бы опубликовать. Настройки самого OpenCode не создают такой обход режима чтения.
- [ ] Подготовка свежей среды восстанавливает закреплённые 38 Matt Pocock Skills с проверкой состава и содержимого по существующему lock и обеспечивает их обнаружение и чтение именно OpenCode, включая `to-spec`, `to-tickets` и `implement-spec`.
- [ ] Агент получает актуальные инструкции, текущий трекер `skaffman41/ai-for-developers-project-387` и команду `mise run check`; исторические ссылки проекта 386 сохраняют исходное значение.
- [ ] Явно заданы выбранная модель `opencode/glm-5.3-flash-free`, отсутствие платного fallback, `share: false`, оба mentions, 30 минут и не более одного активного запуска на Issue/PR без автоматической отмены текущего. Для разных типов комментариев к одному PR используется общая область concurrency.
- [ ] Ошибка конфигурации, недоступность модели или квоты дают понятный незавершённый результат без автоматической смены модели; способ проверки этих отказов и границы выполненных проверок зафиксированы без выдачи локального результата за живой прогон.
- [ ] Описание обычного вызова и актуальные проектные инструкции согласованы с подготовленным поведением; пользователь понимает, где смотреть Actions и что живой результат пока ожидает приёмки.
- [ ] Существующий workflow Hexlet сохранён побайтно; пройдены соответствующие проверки конфигурации, форматирования и ссылок, полный существующий `mise run check` и необходимое независимое ревью. Новые автотесты не добавлены.
- [ ] Есть отдельный локальный коммит этой задачи и отчёт с SHA, результатами проверок, границами доказательств и указанием, что публикация кода и живая приёмка ещё не выполнены.

## Testing Decisions

Наследуются Testing Decisions спецификации #3. Здесь проверяется поведение на границе конфигурации запуска и эффективных разрешений runtime: подходящие/неподходящие события и авторы, доступность инструкций и скиллов, отсутствие записи и чистота дерева после подготовки. Применяются существующие проверки и разовые диагностические команды без новых файлов автотестов. Реальный путь «комментарий → Actions → ответ» выполняется в финальной задаче после разрешённой публикации.
