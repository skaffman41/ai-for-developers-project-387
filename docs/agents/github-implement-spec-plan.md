## Порядок отдельной реализации

1. На основе существующего #25 согласовать отдельный runtime spec, Testing Decisions и граф по [workflow](development-workflow.md#план-до-реализации), затем сохранить новый planning snapshot до реализации. Сейчас новые Issues не создаются, #26–#31 не дублируются. Синтаксис явно выделенного запуска, например `/oc publish $implement-spec 17`, распознаётся детерминированно; это лишь предложение будущей команды. Обычные publish/read-only сохраняют прежние полномочия. Принимать только Issue согласованного spec текущего репозитория, проверять полные тексты/комментарии, native parent/blocked_by, snapshot hashes, отсутствие циклов и уже интегрированные результаты. Модель и права не выбираются текстом Issue.
2. Из доверенного bootstrap подготовить неизменяемый helper управления графом вне checkout. В реестре запуска сохранить run_id/run_attempt, исходную ветку адаптера, базовый SHA, разрешённый spec, задачи, workspace/ref каждого исполнителя и expected head. Временные пути лежат под отдельным RUNNER_TEMP корнем; refs имеют префикс текущего запуска. Helper принимает структурированные операции и фиксированные аргументы, исключает произвольный shell и записи main/protected refs.
3. Добавить primary coordinator и отдельные implementer/merger агенты. Для первой реализации предпочесть отдельный процесс обычного CLI с явным cwd каждого worktree, новым session/config/XDG state и проверкой эффективных прав, а не предполагать поддержку cwd встроенным task. Прототипом без модели подтвердить механизм и границы прав до запуска графа. Каждый вызов исполнителя — свежая сессия/контекст, одна задача, worktree/ветка от текущего integration SHA. Исполнитель пишет только свой worktree, читает pointers на spec/Issue/снимок; скиллы из прежнего lock. Coordinator не редактирует результаты за исполнителей. Merger работает только с зарегистрированными ветками и готовыми SHA. Два read-only reviewer сохраняют независимые оси.
4. Scheduler выбирает frontier по native blockers. Задача становится готовой зависимостью лишь после успешных критериев/check/review, отдельного Conventional Commit с её номером, чистого worktree, записанного SHA/tree и merge/ancestry в integration. Отменённая, failed, not_planned задача не разблокирует граф. Перед сдачей параллельный исполнитель включает новый integration tip в свою ветку и повторяет применимые проверки; merger сверяет base/tree и не принимает устаревший отчёт. При конфликте merger останавливает этот frontier и передаёт конкретный конфликт исполнителю; чужие изменения не сбрасываются.
5. До trusted promote исходные HEAD/tree ветки адаптера остаются неизменными; coordinator и исполнители не имеют операции записи в этот checkout. Только доверенный publisher после всех проверок собирает integration в исходную ветку PR; проверить неизменность её имени, ожидаемый remote head, отсутствие чужих изменений и всех временных файлов, сохранность hexlet-check/snapshots, ancestry всех готовых задач. Финальный check и две оси ревью на совокупном diff обязательны. Нужен технический барьер публикации: текущий совмещённый adapter run не имеет надёжного hook между моделью и финализатором. Рекомендуемый следующий режим отделяет ordinary CLI исполнителей от доверенного no-model publisher; credential выдаётся только publisher после независимой проверки графа/check/review и текущего remote head. Совместимость с OIDC/App и сохранение исходной ветки подтвердить отдельным прототипом на закреплённом исходнике; молча изменять стандартный адаптер нельзя. Лишь полностью готовое дерево допускает push/create/update PR. Ошибка или timeout не разрешают автоматически публиковать частичный граф. Merge в main не является операцией helper/модели.
6. Cleanup удаляет только зарегистрированные чистые worktree этого запуска после сохранения результатов. Проверять реальный путь, принадлежность ref и чистоту; не использовать глобальный prune/reset/clean. Сохранить доказательства: spec/version, ticket->commit/tree, frontier transitions, commands/checks/reviews, итоговый PR head. Токены, env и credential config не входят в логи/артефакты.

## Владение графом, отмена и повторные запуски

Два запроса из Issue и PR к одному spec должны иметь одного владельца графа. Для первого режима рекомендуется одна общая очередь всех допущенных manual graph/publish запросов репозитория: это проще доказать, чем несколько пересекающихся locks, и не требует Actions write. После отдельного решения можно сузить её до spec/PR с доказанным порядком блокировок. Обычные комментарии отсекаются до очереди. Бюджет #26 остаётся на PR и считает каждую допущенную попытку родительского запуска; дочерние процессы не сбрасывают счётчик. Re-run failed jobs повторно проходит admission в job перед моделью.

Сохранить предел 30 минут; timeout/отмена останавливает исполнителей, затем отдельный no-model reporter. Частичный граф не публикуется в PR. Рекомендуемый перенос между отдельными командами — диагностический checkpoint (ограниченный Git bundle/patch + spec/version/ticket SHA), создаваемый доверенным шагом без credentials и проверяемый заново при resume; это входные данные, не доказательство приёмки. До внедрения и проверки такого механизма следующий запуск начинает граф заново от подтверждённого PR head. Политику checkpoints/retention закрепить в отдельном runtime spec; расширение timeout, Actions dispatch/write и внешнее хранилище не подразумеваются.

## Проверки runtime до живого запуска

- Debug/verify и реальная проверка границ записи: разрешения текущего V1 не являются OS sandbox, поэтому одной allowlist недостаточно для доказательства изоляции shell-команд. Фактическая запись в соседний worktree, общий Git metadata, publisher checkout и состояние helper должна завершаться отказом. Затем проверить эффективные инструменты каждого агента: coordinator запускает только разрешённые роли; implementer не создаёт произвольных подагентов; merger не вызывает модель разработки; reviewers только read/glob/skill. Обычный read-only не получает новых прав.
- Helper с временным Git-репозиторием: пара независимых задач и зависимая, неверная база, цикл, rejected blocker, конфликт, чужая грязная копия, неправильный ref/path, запись main, попытка доступа к .git/env, смена remote head, отмена и cleanup. Отдельно проверить синхронизацию параллельных веток с пересечением генерируемых файлов. Проверять наблюдаемые refs/деревья и отказ без побочных эффектов.
- Интеграция с закреплённым адаптером: исходная ветка сохраняется, per-ticket commits доходят до PR, незавершённый граф не публикуется, повторная команда проверяет уже сохранённые результаты. После успеха первой задачи испытать отказ второй, падение final check/review, ошибку модели и timeout: исходные HEAD/tree неизменны, push/PR отсутствуют. Отдельно проверить одновременные запросы одного spec из Issue и PR, устаревший checkpoint, взаимодействие бюджета #26, rerun/timeout и no-model reporter. Никаких Actions write или account administration у модели.
- Полный mise run check, независимые Standards/Spec и свежий bootstrap test из main. Полноценная живая приёмка после отдельной команды: маленький согласованный spec с двумя независимыми задачами и merger, затем отказ допуска/timeout. Ни docs-only пример, ни открытый PR не доказывают работу runtime.

## Ограничения следующего этапа

Текущий предел модели/job — 30 минут. Для больших графов нужно отдельно решить продолжение между запусками и предотвращение публикации незавершённого дерева; не увеличивать timeout и не добавлять Actions dispatch/write скрыто. Если потребуется orchestration с actions:write, новый сервис, другой App, платная модель или более широкие права — остановиться и запросить конкретное расширение. Уже разрешённые временные worktree/ветки и роли повторного согласования не требуют.
