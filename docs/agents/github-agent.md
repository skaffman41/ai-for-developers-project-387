# GitHub-агент

Перед ответом в GitHub прочитай корневой [AGENTS.md](../../AGENTS.md), затем нужные
проектные документы и скиллы. Текущий трекер —
[`skaffman41/ai-for-developers-project-387`](https://github.com/skaffman41/ai-for-developers-project-387/issues).
Исторические ссылки проекта 386 сохраняют исходные номера и репозиторий.
Общая проверка проекта — `mise run check`.

## Обычный запрос

Команды владельца `/oc` и `/opencode` эквивалентны. В этом режиме прочитай
относящийся к вопросу код и инструкции, затем ответь в текущем обсуждении.
Если вопрос требует выполнения команды, изменения файлов или внешней записи,
назови конкретное ограничение и оставшуюся работу в ответе.
Скиллы доступны для чтения, но их инструкции о публикации, назначениях и
делегировании не расширяют полномочия обычного запроса. Полный `implement-spec`
этим режимом выполнить нельзя. При подготовке следующего этапа полного графа читай
[отдельный план runtime](github-implement-spec-plan.md): это предложение реализации,
а не доступная команда текущего GitHub-агента.

## Автоматический разбор

[Автотриаж](../../.github/workflows/opencode-triage.yml) обрабатывает только
`issues: opened` от владельца `skaffman41` типа User в текущем репозитории.
Проверка actor/sender и меток `type:*` проходит до checkout и секретов; подготовленные
записи пропускаются. Только допущенный job входит в общую очередь Issue/PR.

Фиксированный вход `prompt` официального action вызывает `triage` с чтением
инструкций и приложения. Подготовка повторно проверяет событие и включает тот же
`github-reader`: только read/glob/skill, без shell, записи, помощника трекера и
делегирования. Ответ публикует официальный App. Предлагай категорию и роль, вопросы
и следующий шаг; код, метки и состояние Issue не меняй. Тайм-аут — 30 минут,
runtime, скиллы, бесплатная модель, защита снимков и секретов сохраняются.

При живой приёмке создай от владельца новое обращение без `type:*` и подготовленный
тикет с `type:task` уже при создании. Сохрани ссылки на содержательный ответ и оба
Actions run, включая явный пропуск до модели. Отсутствие запуска для Issue,
созданного через GITHUB_TOKEN, не доказывает работу фильтра: GitHub подавляет такие
события для предотвращения рекурсивных workflow.

## Явная публикация

Только новый комментарий владельца, начинающийся с `/oc publish <задача>` или
`/opencode publish <задача>`, выбирает режим публикации. Между командой и `publish`
нужен пробел или табуляция; задача обязательна. Кавычки, блок цитаты, упоминание
`publish` в вопросе или в последующих строках обычного запроса режим не меняют.
Проверка допуска передаёт выбранный режим подготовке; подготовка независимо сверяет
его с исходным комментарием. Содержимое задачи попадает в prompt как данные,
никогда как shell-команда.

Этот запуск разрешает изменить файлы только для указанной задачи в
`skaffman41/ai-for-developers-project-387`. Стандартный адаптер отправляет рабочую
ветку и создаёт PR из Issue либо обновляет текущий PR. Сохраняй ветку, которую
подготовил адаптер: он замечает собственные коммиты агента и публикует их после
ответа. Отдельные push и создание PR инструментами модели не нужны и запрещены.
Другие задачи, репозитории и последующие комментарии требуют своего разрешения;
merge остаётся отдельной командой и этим workflow не выполняется.

Перед изменениями файлов прочитай [development-workflow.md](development-workflow.md),
согласованный план, Issue и блокеры. Изменения файлов сохраняют требования плана,
отдельных Conventional Commits с номером задачи, полного `mise run check` и
независимого `code-review`. Для существенной правки вызови две независимые оси
через `review-standards` и `review-spec`: передай каждой полный текст `git diff HEAD`
и `git diff --cached`, исходный SHA и критерии. Исправь замечания и повтори затронутые
проверки до коммита. Новые автотесты добавляй только по прямому поручению.
Заканчивай ответ с чистой закоммиченной копией: укажи SHA, проверки и ревью.
При блокировке отмени собственные незакоммиченные правки командой
`git restore --worktree --staged -- <свои изменённые пути>`, удали собственные новые
пути через `git clean -fd -- <свои новые пути>` и опиши невыполненное в ответе,
иначе финализатор может опубликовать незавершённую работу. Начальный чистый checkout
проверяется до адаптера; откат касается только работы этого запуска.
Для простой правки документации объём ревью определяется тем же workflow.

Если запрос меняет только записи трекера и checkout остаётся чистым, сообщи ссылки
на результат без установки, сборки и тестирования приложения. Для подготовки и
полного check задай shell timeout не меньше 600000 мс, чтобы прерывание команды
не оставляло работающий сервер проверки.

Эти полномочия относятся только к GitHub-команде `publish`. Локальные
`implement`/`implement-spec` по-прежнему требуют отдельных явных разрешений на
push, PR и merge. Чтение скилла не выдаёт дополнительных полномочий.

## Подготовка и граница доверия

[Workflow](../../.github/workflows/opencode.yml) обрабатывает только новые
`issue_comment` и `pull_request_review_comment`. Задание `authorize` работает без
checkout, OIDC и ключа модели: проверяет репозиторий, автора `skaffman41` типа `User`,
аккаунт инициатора, команду в начале комментария и через GitHub API — открытый PR
с head/base в целевом репозитории. Fork отклоняется для обоих типов комментариев.
Событие `pull_request_target` не используется.

В общую очередь Issue/PR входит только допущенный job `answer`. Ответы бота и
комментарии без команды проходят лишь проверку допуска и не вытесняют ожидающую
команду владельца. В одной группе работает один ответ, без отмены работающего;
для ручных команд `queue: max` сохраняет очередь ожидающих job. Автотриаж использует
ту же группу, но сохраняет стандартный предел одного ожидающего job.

Ручное задание `answer` ограничено 60 минутами. Новое значение действует только
после интеграции workflow в `main`; открытый PR не меняет bootstrap запуска.

Только после допуска checkout получает bootstrap из основной ветки с
`persist-credentials: false`. `contents: read` и `id-token: write` соответствуют
[стандартной авторизации официального App](https://opencode.ai/v1/docs/github/);
`issues: write` того же задания и переданный им `GH_TOKEN` дают закреплённому gh
доступ к Issues целевого репозитория (см. «Закреплённый runtime» ниже).
Секрет `OPENCODE_API_KEY` передаётся исключительно шагу action. Его значение не
нужно для подготовки и не должно попадать в репозиторий, ответы или диагностику.

Bootstrap читается из default branch (`main`), поэтому правка подготовки в открытом
PR не расширяет полномочия текущего запуска. После отдельно разрешённого merge
нужно новое событие. Для ручного PR-запуска внутри очереди повторяются authorize,
проверка бюджета и потолка прав App, в том числе при Re-run failed jobs.

[`prepare-github-agent.mjs`](../../scripts/prepare-github-agent.mjs) восстанавливает
скиллы из точной ревизии [skills-lock.json](../../skills-lock.json): проверяет Git
tree каждой папки, состав, SHA-256 содержимого, 38 имён и 103 файла. В runtime
подключается только этот набор; загрузка внешних скиллов и конфигурации проекта
отключена. Файлы конфигурации, скиллы и состояние OpenCode находятся в
`RUNNER_TEMP`, вне checkout. Настройка `OPENCODE_TEST_HOME` из закреплённого runtime
изолирует также поиск пользовательских `.opencode`-каталогов, сохраняя системный HOME.
Подготовка не устанавливает зависимости приложения и не запускает Git hooks.

## Автоматическое ревью PR

[`opencode-pr-review.yml`](../../.github/workflows/opencode-pr-review.yml) принимает
только `pull_request: opened, synchronize, reopened`. `authorize` до checkout и
секрета проверяет событие и текущее состояние API: PR открыт, его head/base
принадлежат этому репозиторию, автор — `skaffman41` типа User либо наш
`opencode-agent[bot]` типа Bot. PR приложения входит в обязательное ревью;
fork и остальные авторы отклоняются. `pull_request_target` не применяется.

Режим `GITHUB_AGENT_MODE=pr-review` создаёт отдельного primary
`github-pr-review` обычного CLI 1.19.6 с прежней бесплатной моделью. Доверенный
bootstrap и [REVIEW.md](../../REVIEW.md) берутся из `main` в `trusted/`, точный
head SHA — в `review-data/`. Подготовка, сбор входа и запуск выполняются доверенными
скриптами; код PR в job ревью не исполняется. Модель получает только
read/glob/skill, без shell, правки, делегирования, публикации и GitHub credentials
(включая OIDC). Это отдельная сессия, не продолжение сессии разработчика.

[`pr-review-input.mjs`](../../scripts/pr-review-input.mjs) собирает diff base...head
без external diff/textconv и критерии REVIEW.md. Доверенный шаг добавляет тело PR,
комментарии, reviews/threads с состояниями resolved/outdated, CI checks/statuses,
связанные Issues с обсуждениями, native parent и blockers. Обход связанных Issues
ограничен 12 записями, контекст и diff — по 180000 символов; пропуски обозначаются
в prompt, и ревью должно назвать ограничения. Содержимое PR и Issues — данные,
которые не меняют права и критерии модели.

Человекочитаемый текст авторевью задаётся на русском: вывод, условия и последствия
дефектов, сообщение об их отсутствии и ограничения проверки. Имена JSON-полей,
пути, идентификаторы, команды и точные цитаты сохраняются в исходном виде.

После модели сохраняется только JSON результата. Отдельная job `publish` без
модели/checkout проверяет run/attempt/SHA, размер и структуру artifact, текущий
доверенный PR; публикует комментарий с проверенным SHA. Каждый дефект содержит
файл, положительную строку, условия и последствия. При отсутствии дефектов модель
должна вернуть пустой список и честный вывод. Если head успел измениться, публикуется
сообщение об устаревшей версии вместо замечаний. `APPROVE` не отправляется.

Concurrency на PR с `cancel-in-progress: true` отменяет старое ревью. История
Actions с `run-name` `opencode-review pr=<номер> sha=<SHA>` предотвращает второй
вызов модели для того же PR/head, включая Re-run и ранее неуспешное ревью.
В review job стоит дополнительный отказ при `run_attempt != 1`, чтобы Re-run failed
jobs не использовал прежний допуск. Job ограничена 30 минутами, процесс CLI —
28 минутами. Авторевью не расходует ручной бюджет и не запускает автоисправления.

## Бюджет ручных PR-команд и reporter

В `opencode.yml` обе разновидности ручных комментариев на PR, read-only и publish,
имеют общий бюджет 3 допущенных попытки. Он проверяется внутри очереди PR без
отмены работающего job (`queue: max`). Источник — полная история Actions этого
workflow с `run-name` `opencode manual #<номер>` и успешными шагами
`Record admitted manual attempt <SHA>` для каждого `run_attempt` обоих событий.
Отмена, тайм-аут и ошибка после маркера расходуют попытку; ошибка до маркера её не
расходует. Re-run заново проходит authorize и budget до checkout/секрета модели.
Неполная или противоречивая история останавливает допуск. Комментарии и метки
служат отчётами, а не состоянием бюджета. Для обычного Issue лимит PR не применяется.

Job token имеет `actions: read`. Адаптер отдельно получает App credential через
OIDC, поэтому до маркера проверяется и App `opencode-agent` с id `1549082`:
`actions` и `administration` допускаются лишь отсутствующими либо `read`.
Потолок App не выводится из прав `GITHUB_TOKEN`; модель не получает Actions write
или управление аккаунтом. Изменение потолка останавливает запуск до модели.

После остановки исходного workflow независимые `workflow_run: completed`:
[`opencode-report.yml`](../../.github/workflows/opencode-report.yml) для ручных
команд и [`opencode-pr-review-report.yml`](../../.github/workflows/opencode-pr-review-report.yml)
для авторевью — выполняют no-model reporter со своим тайм-аутом 5 минут.
Reporter не получает ключ, OIDC или checkout PR. Он проверяет происхождение
run/attempt, затем сообщает `timeout`, `agent_failed` или `infra`, последний
известный SHA, ссылку и «нужен человек»; manual reporter также сообщает
`limit_exhausted`. Ручной reporter дедуплицирует свой комментарий по run/attempt;
review reporter пропускает недоверенный, закрытый или уже устаревший PR.
Автоматический повтор модели и платный fallback отсутствуют.

## Браузерная проверка версии PR

Job `browser` из `opencode-pr-review.yml` запускается для доверенного PR независимо
от дедупликации модели и ограничена 15 минутами. У неё только `contents: read`,
без секрета модели и OIDC. Checkout получает точный `head.sha` события;
`git rev-parse HEAD` сверяется с ожидаемым SHA до установки и браузерных тестов.
После push новая `synchronize` проверяет новую версию.

[`playwright.pr.config.ts`](../../playwright.pr.config.ts) включает trace и
скриншоты также при успехе; обычная конфигурация приложения сохраняет диагностику
падений. Artifact `pr-browser-<run_id>-<run_attempt>` (14 дней) содержит
`expected-sha.txt`, `actual-sha.txt` при доступном checkout, статус проверки,
`run-report.md/html`, `playwright-report/` и `test-results/` при их наличии.
Отчёт и загрузка выполняются также после ошибки подготовки, пока job не отменена;
до запуска теста trace/скриншотов нет. Artifact подтверждает конкретное дерево,
а не всю бизнес-приёмку. `app-check` и неизменяемый `hexlet-check` сохраняются.

## Закреплённый runtime

Официальный action закреплён на
[`f4e363c8295fa90a03dddc451882fffe8fbce357` (v1.19.6)](https://github.com/anomalyco/opencode/blob/f4e363c8295fa90a03dddc451882fffe8fbce357/github/action.yml),
runtime — `1.19.6`. У action нет входа `version`; официальный installer учитывает
переменную `VERSION`. Для точного запроса `curl -sf` к `releases/latest` в
официальном action оболочка `BASH_ENV` возвращает локально закреплённый tag
`v1.19.6`: ключ cache и installer используют одну версию без лишнего запроса к API.
Остальные вызовы curl выполняются исходной программой. Перед каждым вызовом
`opencode` оболочка проверяет реальную версию: несовпадение останавливает запуск.
Официальный адаптер не изменяется.

Конфигурация использует V1-поля `permission`, `bash`, `task` этой версии;
[актуальные V2-документы](https://opencode.ai/docs/permissions/) описывают другой
формат. Для ручных команд основной агент `github-reader` либо `github-publisher` выбран через `default_agent`, поскольку
закреплённый адаптер не передаёт вход `agent` в prompt. В конфигурации и основном,
и малом агенте задана только `opencode/deepseek-v4.1-flash-free`; провайдер ограничен
единственной моделью. Перед запуском подготовка читает публичный каталог OpenCode: отсутствие модели, поддержки инструментов или подтверждённых нулевых цен текста и cache read останавливает запуск. Ошибка сети также завершает подготовку без модели. Платного fallback нет. Автообновление, snapshots, formatter,
LSP и публикация сессий отключены.

Все инструменты по умолчанию запрещены. В обычном режиме разрешены только `read`,
`glob` и чтение закреплённых `skill`; запись, shell, делегирование, web/MCP и
неизвестные инструменты остаются запрещёнными. Чтение вне проекта разрешено только для
проверенных скиллов. Непосредственно перед `github run` runtime без ключа модели
показывает эффективные инструменты и найденные скиллы. Проверка требует ровно
разрешённые инструменты, обнаружение и прочитанное содержимое всех 38 скиллов;
отдельно исполняется инструмент `skill` для `to-spec`, `to-tickets`, `implement-spec`.
Ошибка любой проверки останавливает адаптер до вызова модели.

Авторизацию gh для Issues даёт `GH_TOKEN` из `github.token` задания `answer` с правом
`issues: write` на уровне workflow. Этот токен не предназначен для Git push и PR — их
выполняет стандартный адаптер через собственную авторизацию App, что соответствует
правилу раздельной проверки Git-авторизации и доступа к Issues. Подготовка в режиме
публикации разово проверяет рабочую авторизацию командами `gh auth status` и
`gh repo view` из [skills.md](skills.md#github-cli) и останавливает запуск без неё.

В публикации дополнительно доступны `edit`/`write`, `bash` с разрешёнными командами
локальной подготовки, проверок, просмотра Git, помощника трекера из
[issue-tracker.md](issue-tracker.md), `git add -- <пути>` и коммита с `-m`/`--message`, а также
`task` только для двух указанных агентов ревью. Их отдельные конфигурации разрешают
только чтение и получают diff в тексте задачи, запрещают shell, запись и дальнейшее делегирование, закрепляют ту
же бесплатную модель. Помощник вызывает закреплённый gh с фиксированными endpoint,
методом и хостом для каждой операции трекера. Модель передаёт JSON из служебного
каталога, без произвольных флагов CLI или путей входных файлов; прямые команды gh
остаются закрытыми. Рабочая копия помощника находится вне checkout и защищена от
инструментов правки. Формат запросов — в разделе
[GitHub Actions](issue-tracker.md#github-actions). Просмотр Git ограничен точными командами и путями после `--`, без произвольных
опций. Откат разрешён только для явно указанных собственных путей. `--amend`,
`--no-verify` и `-n` для коммита отклоняются. Файлы окружения, `.git` и
обязательный workflow Hexlet закрыты для инструментов правки. Подготовка также
закрывает для правки каждый файл снимков планов, уже сохранённый в
bootstrap-checkout: список таких файлов генерируется при подготовке, поэтому будущие
версии `vN+1` и новые файлы текущего запуска остаются редактируемыми. Неизменяемость
принятых версий остаётся и правилом
[workflow](development-workflow.md#план-до-реализации); новые снимки сохраняются
отдельным planning-коммитом до реализации.
Это разрешения инструментов доверенного запуска, а не отдельный OS sandbox:
разрешённые проектные команды исполняют код репозитория. Поэтому публикуемый объём
всё равно ограничивается задачей и проверяется ревью.

`grep` также запрещён: этот инструмент выбранной версии не применяет правила
`read` к содержимому найденных файлов и при явном пути `.git` может прочитать
локальную конфигурацию с авторизацией адаптера. Поиск файлов выполняется через
`glob`, чтение — через `read`, который запрещает `.git` и файлы окружения.
V1 проверяет пути лексически, поэтому подготовка также отклоняет уже существующие
symlink в checkout и задаёт локальный `core.symlinks=false`. Последующий checkout
PR стандартным адаптером создаёт обычный файл с текстом цели для Git-mode `120000`,
а не ссылку, обходящую запреты чтения. Настройка относится к свежему Actions-клону.

Стандартный адаптер автоматически публикует найденные изменения после ответа.
Поэтому перед его запуском также требуется пустой
`git status --porcelain --untracked-files=all`; генерация runtime не должна создавать
`.opencode`, lockfiles или другие изменения в checkout. После ответа чистоту и
отсутствие опубликованной ветки/PR проверяет живая приёмка.

## Проверки и незавершённые запуски

Без App и ключа можно выполнить подготовку с временными `RUNNER_TEMP` и
`GITHUB_ENV`, загрузить полученные переменные и запустить закреплённый runtime:

```sh
opencode debug agent github-reader
opencode debug skill
opencode debug agent github-reader --tool skill --params '{"name":"to-spec"}'
opencode debug agent github-reader --tool write --params '{}'
opencode debug agent github-reader --tool bash --params '{}'
opencode debug agent github-reader --tool task --params '{}'
git status --porcelain --untracked-files=all
```

Для подготовки задай `GITHUB_EVENT_PATH` с исходным JSON события и
`GITHUB_AGENT_MODE=read-only` либо `publish` из задания допуска. В режиме публикации
подготовка также требует `GH_TOKEN` с доступом к Issues целевого репозитория и разово
проверяет его командами `gh auth status`/`gh repo view` из [skills.md](skills.md#github-cli).
Несовпадение останавливает подготовку. Для публикации используй `github-publisher`
вместо `github-reader`, проверь обе конфигурации `review-standards`/`review-spec` и
разовые пробы новых разрешений: чтение трекера помощником, создание нового снимка
и отказ записи в существующий снимок. Для проверки запрета используй `write` и
сверь хеш файла до/после: ошибка отсутствующего `oldString` не доказывает отказ
разрешения. Прямые gh-команды, лишние операции помощника и входные файлы вне
служебного каталога также должны завершаться отказом.

Для `pr-review` задай событие доверенного `pull_request` одного из трёх типов,
`GITHUB_AGENT_MODE=pr-review`, отдельный checkout точного SHA в
`GITHUB_REVIEW_DIRECTORY`; подготовку выполняй из bootstrap. Из review checkout
сохрани `opencode debug agent github-pr-review` и `opencode debug skill` в
`$GITHUB_AGENT_ROOT/agent.json` и `discovery.json`, затем из доверенного окружения
выполни `node "$GITHUB_AGENT_ROOT/verify.mjs"`. Проверь разрешённые read/glob/skill
и фактические отказы write/edit/bash/task/grep/web/MCP без ключа и модели.
Verify требует точную модель, ровно разрешённые инструменты и чтение всех 38
закреплённых скиллов. CLI запускается отдельно через
[`run-pr-review.mjs`](../../scripts/run-pr-review.mjs); reviewer не публикует результат.

В обычном режиме последние три обращения к инструментам должны завершиться отказом; изменение
файла не требуется для доказательства запрета. Команды `debug` не вызывают модель.
Для конфигурации также применяются YAML-разбор, форматирование, ссылки,
`git diff --check`, полный существующий `mise run check` и независимое ревью.

Отсутствующий Secret отклоняет оболочка; неверную конфигурацию отклоняет runtime.
При ошибке модели/квоты официальный адаптер завершает Actions с ошибкой и пытается
ответить в обсуждении её текстом. Автоматической смены модели нет. Для живой
проверки отказов в #6 фиксируются отдельный неуспешный run и ответ/ошибка без
раскрытия ключа; платная модель для проверки не используется.

Локальная проверка эффективных разрешений обоих режимов подтверждает подготовку
#4/#5. Установка App, Secret, фактическая бесплатная работа модели с инструментами
и путь «комментарий → Actions → ответ» остаются критериями
[#6](https://github.com/skaffman41/ai-for-developers-project-387/issues/6).

## Отдельный режим аудита зависимостей

`dependency-audit.yml` обрабатывает только `schedule` и `workflow_dispatch` из
`main` целевого репозитория. Контекст комментария, `/oc`, PR и GitHub App для этого
входа не требуются. Подготовка использует те же закреплённые CLI 1.19.6, бесплатную
модель и проверенные 38 Matt Pocock Skills; `dependency-auditor` получает только
read/glob/skill. Данные отчёта и Issues — недоверенные свидетельства, они не
разрешают новые операции. Существующие режимы комментариев и PR сохраняют свои
границы.

После валидации источника и сопоставления находок runner фиксирует `model-input/`:
точные байты `audit-report.json`, проверенный `provenance.json`, `findings.json` и
`issues.json` без служебного журнала. Только этот дочерний каталог доступен модели
вне проекта и закреплённых скиллов. Родительские result, события и диагностика
запрещены правилами read/external_directory; исходный полный inventory остаётся
артефактом и используется publisher. Prompt отделяет факты текущего источника от
исторических текстов Issues. Резервный `result.json` сохраняется для публикации
после прерванного анализа.

После проверки эффективных инструментов и обнаруженных скиллов создаётся внешний
`audit-ready.json`; без него runner не вызывает модель. Её процесс получает ключ
бесплатной модели, но не GitHub/Actions credentials. Shell, запись, делегирование,
web/MCP, публикация и адаптерный finalizer недоступны. Отдельный детерминированный
runner имеет `contents: read`/`issues: write` и `actions: read` для replay-источника.
Он создаёт максимум одну входящую задачу high/critical и обновляет тело единственного
журнала в `skaffman41/ai-for-developers-project-387`. Журнал определяется точным
названием, автором `github-actions[bot]` типа Bot и маркером в первой строке;
цитирование маркера в обычном Issue не делает его целью записи. Endpoint, метод и поля API
выбираются кодом, а не ответом модели. Закрытый журнал не заменяется новым.

Повтор после неоднозначного ответа создания сначала заново читает полный inventory
и ищет маркер журнала; создания без успешного чтения нет. Если найдено несколько
журналов, публикация останавливается с ошибкой. Исходный отчёт и диагностика
сохраняются за пределами checkout, артефакты — 30 дней. Ошибки подготовки/модели
не превращаются в чистый аудит. Поиск находок использует стабильную идентичность
«тип данных + пакет + advisory», все страницы открытых/закрытых Issues и повторную
проверку перед POST. PR и журнал исключаются. Известные задачи не изменяются;
новые остаются входящими без назначения и роли ready-for-agent. После неоднозначного
POST выполняется чтение inventory; сохранённый в задаче маркер восстанавливает
результат после частичной публикации.

Ручной `input=replay` читает точные байты `audit-report.json` и исходный provenance
из проверенного artifact исходного run/attempt. Доверенная проверка требует этот
репозиторий, completed main audit, закреплённый SHA события, доступный artifact и
совпадающие report/lockfile SHA-256 и подтверждённую в provenance валидацию сбора. Checkout закреплён на `github.sha`; продвижение
main после события не меняет исследованный SHA. Из ZIP читаются известные файлы
данных без извлечения или исполнения. Исходное происхождение сохраняется отдельно
от текущего replay; ошибочный источник останавливает аудит без подмены свежим npm.
`input=educational` генерирует синтетический отчёт вне checkout, явно помечает
результат/журнал/задачу и сохраняет отдельную идентичность даже при поиске по тексту.
Публикация ограничена общим дедлайном 50 секунд; чтение replay — 90 секундами.
Сценарий и будущая живая приёмка описаны в
[README](../../README.md#регулярный-аудит-зависимостей).

## Финальная живая проверка

1. После отдельного разрешения на публикацию и включение workflow в `main`
   проверь установку официального App на проект 387 и метаданные Secret
   `OPENCODE_API_KEY` без чтения значения. Зафиксируй SHA основной ветки.
2. В Issue отправь обычную команду: `/oc Прочитай AGENTS.md и доступные скиллы.
Назови текущий трекер, to-spec, to-tickets, implement-spec и общую команду
проверки.` Сохрани ссылки на комментарий, ответ приложения и успешный Actions
   run; проверь отсутствие опубликованных изменений, ветки и PR этого запроса.
3. Согласуй конкретную небольшую правку README из примера в
   [README](../../README.md#агент-в-github) и отдельным новым комментарием отправь
   её команду `publish`. Пример в документации сам по себе запуск не разрешает.
4. Свяжи команду, ответ, Actions run, SHA, diff и созданный/обновлённый PR. Проверь
   ожидаемую единственную правку, Conventional Commit с #6, успешные существующие
   проверки, отчёт о необходимом ревью и отсутствие merge. Решение о merge
   принимает владелец отдельно.
5. В отчёте #6 сопоставь все AC-01–AC-08 с живыми свидетельствами. Отдельно
   зафиксируй бесплатность модели, работу инструментов и сценарий понятного отказа
   без платного fallback. Неполную приёмку оставь открытой с конкретными пробелами.

## Живая приёмка ревью и бюджета

Локальные YAML/mock API, debug/verify, полный check и независимые Standards/Spec
проверяют подготовку [#26](https://github.com/skaffman41/ai-for-developers-project-387/issues/26),
но не доказывают новые события Actions. После отдельно разрешённого merge
инфраструктуры в `main` и отдельной команды живой приёмки:

1. Зафиксируй SHA `main` и создай новое доверенное событие PR. Свяжи run, точный
   head и опубликованный комментарий ревью. Отдельно проверь PR нашего App,
   отклонение fork/другого автора до модели, отсутствие `APPROVE` и автоисправлений.
2. Обнови head и проверь отмену старого ревью, новый SHA и browser artifact.
   Re-run того же SHA не должен вызвать модель повторно. Проверь JSON/report и
   trace/скриншоты успешного прогона, затем диагностику падения; ошибка подготовки
   должна дать отчёт без выдуманных браузерных материалов.
3. На отдельном PR сверь три допущенные ручные попытки обоих видов комментариев,
   read-only/publish и `run_attempt`; четвёртая останавливается до секрета.
   Сопоставь маркеры Actions, отмену/тайм-аут и независимый reporter с «нужен человек».
4. Сохрани команды, run/attempt, SHA, комментарии и artifacts в отчёте #26.
   Если сценарий не проверен, назови пробел. Проверка #6 и локальные прогоны
   не заменяют эти доказательства. Полный GitHub `implement-spec` остаётся
   [следующим этапом](github-implement-spec-plan.md).
